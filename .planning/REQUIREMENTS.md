## Основа и доступ — Phase 1

- [x] **FOUND-01**: чистая схема проходит миграции, повтор seed не размножает строки; health различает обе БД. Проверено с нативной PostgreSQL 16.15; Docker runtime отдельно не подтверждён.
- [x] **ACCESS-01**: врач и пациент входят через login; фактическая роль и принадлежность берутся с сервера.
- [x] **ACCESS-02**: чужие карточки/переписка/опросы/заметки/алерты и решения закрыты; admin без клинического доступа.
- [x] **DATA-01**: десять согласованных MIS/Compass карточек и mapping, SELECT-only роль, явные ошибки источника.
- [x] **PATIENT-01**: список/карточка, доступная часть истории и числовые результаты шкал.

## Главная боль заказчика — Phase 2

- [x] **SURVEY-01**: врач создаёт свой опрос: текст, одиночный/множественный выбор, числовая шкала, обязательность; сохраняет черновик и видит предпросмотр.
- [x] **SURVEY-02**: публикация фиксирует вопросы; новая версия не переписывает старые ответы; назначение только своим пациентам, с необязательным явным сроком.
- [x] **FEEDBACK-01**: пациент отвечает на назначение; проверяются варианты/типы; повтор и конкурентный ответ учитываются один раз.
- [x] **RETENTION-01**: врач видит барьеры, намерения и дословные причины, фактический знаменатель и неизвестные исходы; фильтр по когорте назначений, версии вопросов не смешиваются.
- [x] **ADHERENCE-01**: самоотчёт «выполнено/не получилось/не могу оценить/не применимо» и причина; неответ не становится пропуском лекарства.
- [x] **MOTIVATION-01**: благодарность, реальный прогресс и история участия; одно назначение даёт одно завершение.
- [ ] **CHURN-01**: коммерческий показатель потери клиента с горизонтом и полным источником визитов не утверждён. Вместо догадки доступны отдельные ручные исходы врача и наблюдаемые события JSON; реальный контракт — U04.
- [ ] **CLINIC-01**: состав сводки и владелец настроек подтверждены, API/UI работают; разрешённые срезы/периоды и защита реальных групп — U05. Индивидуальные клинические API admin закрыты.
- [ ] **REWARD-01**: обмен/списание и коммерческие награды — U06. Нематериальные баллы реализованы отдельно, без выдуманных скидок.

## Работа врача и коммуникации — Phase 3

- [x] **MESSAGE-01**: общая история web и явных Patient/Doctor Telegram-симуляторов; polling, курсор API.
- [x] **EVENT-01**: атомарная запись сообщения/шкалы и outbox; уникальность повторов; ограниченные попытки/failed; повтор алерта не размножается.
- [x] **NOTE-01**: приватная заметка с проверяемой ссылкой на первичный ответ/сообщение и задачи врача; чужие источники/чтение закрыты.
- [x] **AUDIT-01**: автор/объект/время клинической работы и доступности; медицинское содержимое не выводится прикладными логами.
- [x] **DECISION-TECH-01**: факт/версия правила/недостающие сведения; врач вручную подтверждает или отклоняет; до решения закрыть нельзя; MIS не изменяется.
- [x] **AVAILABILITY-TECH-01**: ручная доступность врача и честное состояние ожидания у пациента.
- [ ] **ASSESS-01**: числовой API и история PHQ-9/GAD-7 проверены; тексты/интерпретация/версия клинического источника требуют Q05.
- [ ] **ALERT-CLINICAL-01**: предметное согласование правила и сценариев Авиандра — Q05. События исходного scoring помечены как демонстрационные.
- [ ] **FALLBACK-01**: согласованный резервный/кризисный маршрут — Q06. Внешняя передача и помощь не симулируются как совершённые.

## Демонстрация — Phase 4

- [x] **UI-01**: Doctor Web, мобильный кабинет и Telegram-симуляторы; загрузка, пустые состояния, ошибки и scoped данные.
- [x] **DEMO-01**: десять карточек, три технических сценария, матрица проверки, версия схемы, инструкция и честные границы.
- [x] **CONTAINER-01**: production image и полный Compose runtime прошли GitHub Actions (backend/frontend/containers success, run 39650929690). Локальный daemon остаётся недоступным; нативная проверка учитывается отдельно.

## Workflow и измеримость — Phase 5

- [x] **WORKFLOW-01**: синтетический процесс patient/doctor/coordinator/admin: источник → действие/исполнитель → отдельная повторная проверка врача → ручной исход, неизвестность сохранена; docs/MVP_WORKFLOWS.md.
- [x] **ASSESS-VISIBLE-01**: синтетические PHQ-9/GAD-7, ответы по пунктам, сопоставимая история по версиям у своего врача и пациента; один/несколько/нет наблюдений. Проверено: 61 тест, production build, браузер и мобильный экран.
- [x] **METRICS-01**: технический каталог/вычисления с единицами, зрелыми знаменателями, временным срезом и происхождением; контрольные сценарии и отрицательные случаи проверены. Удержание/эффект лечения не объявляются доказанными.
- [ ] **ADMIN-AGG-01**: состав, API/UI, настраиваемость и запрет индивидуальных данных/текстов реализованы. Политика реального пилота/периоды ещё не согласованы (U05); полной продуктовой приёмки нет. По умолчанию без политики числа скрыты.

## Независимая инженерия обязательного ТЗ — Phase 6

- [x] **INBOX-TECH-01** (C01/C03/C05-TECH): общая очередь своих пациентов, cursor/counts, фактический показ строки в активной вкладке, отдельное ручное принятие и переход к исходной карточке; идемпотентный аудит/откат и отрицательные права проверены.
- [x] **SOURCE-PREP-01** (C08-PREP): первичные публикации русских PHQ-9/GAD-7 и официальные точки поиска инструкций/КР с ограничениями; паспорт согласования. Новые клинические правила не внедрены.
- [x] **RESTORE-TECH-01** (T06/C11-TECH): read-only exported snapshot → архив → пустая отдельная restore-test; совпали 18 таблиц, 17 последовательностей, приложение читает восстановленные данные; guards проверены.
- [x] **LATENCY-TECH-01** (T01): 150 успешных контрольных GET; измерены поступление → событие → показ → принятие; техническое время отделено от медицинского SLA/внешней доставки.
- [ ] **TZ-CLINICAL-01** (C04/C06/C07/C08): согласованные кейсы Авиандра, русские тексты/права, источники, терапия и направления — B02.
- [ ] **TZ-URGENT-01** (полный C05/C06): критические признаки, адресат/канал/дежурство/резерв и сроки — B03.
- [ ] **TZ-EMK-01** (C02): контур ЭМК и прямое поступление подтверждённых сведений — B01.
- [ ] **TZ-TRIAL-01** (C10/C11/J06): допустимая среда/апробация и ответственный за применимые требования — B04.

## Сбор по модели пользователя — Phase 7

- [x] **ANALYTICS-DIMENSIONS-01**: четыре явных направления вопроса, категории препятствий, неизменяемая опубликованная разметка; охват/исходные распределения без выдуманного психологического индекса.
- [x] **SURVEY-TIMING-01**: первый видимый пациентский показ, серверное время/единичный аудит, конкурентная идемпотентность; старое завершение не получает вымышленное открытие. Воронка/медианы с числом известных/неизвестных интервалов.
- [x] **DOCTOR-OBSERVATION-01**: приватное наблюдение с направлением/автором/временем/источником; ручной факт из сообщения, исходные ответы и клинические баллы сохраняются.
- [x] **DIARY-01**: добровольная личная запись, явный доступ текущему врачу и его отзыв, идемпотентность/аудит; чужие/admin не читают.
- [x] **ADMIN-AGG-TECH-01**: фиксированный общий контракт с whitelist полей, без текстов/индивидуальных данных/приватных наблюдений/дневника; значение порога не угадано, закрытое состояние по умолчанию; тесты малых групп/дополнений/реальных contributor sets.
- [x] **VISIT-DATA-01**: синтетический JSON МИС: отдельные статусы/инициатор визита, рекомендованное окно и полнота наблюдения; неявка/перенос/отмена не равны отказу. Реальный контракт — U04.
- [x] **MEDICATION-REMINDER-01**: read-only JSON МИС и отдельные личные позиции; фиксированные дни/времена либо произвольное описание, часовой пояс/период/версия, исправляемый явный самоотчёт, симуляция внутри приложения. Внешняя доставка — U07; взаимодействия ЛС не придуманы.
- [x] **PARTICIPATION-POINTS-01**: предложен и реализован `demo-effort-v1`, лимиты UTC и атомарный журнал по трём действиям; повторы/конкуренция/rollback и независимость от симптомов/sharing проверены. Реальный обмен — U06.
- [ ] **DEVICE-IMPORT-01**: конкретный поставщик/модель/показатели/разрешения и Apple/Android-источник — U07. Исследование выполнено, пульс не превращается в тревожность автоматически.

## Применение уточнений — Phase 8

- [x] **CARE-STATUS-01**: три ручных исхода врача и неизвестность до решения; история/автор/причина, idempotency и optimistic revision.
- [x] **CARE-TASK-01**: проверяемый источник, исполнитель, организационный/клинический тип, действие и отдельная проверка результата; чужой/приватный источник закрыт.
- [x] **COORDINATOR-01**: только явно порученные организационные задачи; карточки, шкалы, сообщения, дневник и приватное основание проверки недоступны.
- [x] **ADMIN-POLICY-01**: администратор меняет порог с причиной/историей и проверкой версии; подавление основано на реальных contributor sets и дополнениях, а не числе ответов.
- [x] **DIARY-OBSERVATION-01**: время наблюдения отдельно от внесения, момент/итог дня, необязательные вербальные поля; личная запись по умолчанию, пропуск не нулевой балл.
- [x] **SUPPORT-TEMPLATE-01**: объясняющий редактируемый C1–C7; исключающие варианты защищены UI/API. Обязательный общий каталог и рубрика — U01, автоматического назначения нет.
- [x] **DEMO-SCENARIOS-01**: десять поведенческих профилей, три регулярных и три нерегулярных назначения, явный лекарственный самоотчёт, перенос клиникой с отдельно проверенным действием. Медицинские критерии отбора — U02.

## Научное основание и пересмотр плана — 23.10.2026

До Phase 8 выполнен целевой обзор: docs/RESEARCH_REVIEW.md, docs/RESEARCH_SOURCES.md и docs/INTEGRATIONS_RESEARCH.md. ## За пределами текущей приёмки

LLM, реальные пациенты/МИС/FHIR, автономная терапия, выдуманные медикаментозные правила, внешний кризисный API, полноценная административная панель и промышленная эксплуатация. Реальный Telegram опционален после предоставления бота и безопасной привязки; симулятор принят пользователем.

Требования из PDF не объявляются выполненными целиком. Непокрытые клинические и бизнес-пункты остаются открытыми в очереди, даже если техническая основа уже работает.
