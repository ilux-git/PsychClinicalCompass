# Нагрузка и проверка изменений · 26.10.2026

Последний прогон выполнил **122 749 запросов без ошибок**, но требование максимальной задержки 500 мс **не пройдено**: p95 — 322 мс, p99 — 624 мс, максимум — 1853 мс. p95 не заменяет максимум. [Последний эксперимент R44](evidence/performance-r44-2026-10-26/report.json), [проверки приложения, миграций и шесть снимков интерфейса](evidence/performance-2026-10-26/report.json).

## Что проверялось

Одновременно активны 1000 виртуальных пациентов, 20 врачей и один аналитик. Разгон — 10 секунд, основная часть — 120 секунд. Между действиями каждого пользователя — пауза 0,8–1,2 секунды. Это выбранный интенсивный профиль эксперимента; виртуальная сессия включает время между запросами.

Все 20 операций действительно выполнялись: ответы на опрос, дневник, сообщение, обращения и их обработка, задачи, расписание, баллы, карточки, история и сводки. Добавлены чтение канонических результатов, прогресс сопровождения и клиническая сводка врача. Набор содержит 1000 пациентов и 3000 текущих вымышленных клинических результатов. Повтор отправки уже заполненного авторского опроса проверяет существующий идемпотентный маршрут.

Прогон не охватывает 1000 отрисованных браузеров, массовый вход, пропускную способность новых клинических ответов/решений, внешнюю доставку и задержку через интернет. Результат восьми процессов нельзя переносить на одиночный API по адресу 8780.

## Изменения приложения

- Сводка врача получает определение каждого опроса один раз вместо повторной загрузки для каждого назначения. Аналитика обращений использует подзапрос вместо передачи тысяч идентификаторов. На неизменённой копии при фиксированном времени результаты трёх сводок совпали по контрольным суммам.
- Обязательный журнал чтений получил отдельный ограниченный пул соединений с той же Compass DB. Тест воспроизвёл блокировку при занятом рабочем пуле, затем прошёл с резервом. При ошибке записи по-прежнему возвращается 503 без медицинского ответа; запись завершается до выдачи данных. Сам по себе резерв общую задержку не исправил.
- Миграция `u39_support_lookup_indexes` добавляет два неуникальных индекса: связь события с сообщением и историю явных обращений пациента. В трёх планах запроса исчез просмотр всех 13 855 событий; время выполнения отдельного SQL-запроса сократилось с 2,46–3,33 до 0,16–0,29 мс. Это не время целого экрана или HTTP-запроса.

## Конфигурация стенда

Windows 11, 20 логических процессоров; восемь отдельных API за Caddy. На процесс: рабочий пул 6, резерв журнала 2, пул МИС 1, без дополнительных соединений сверх лимита. Консервативный бюджет всех настроенных пулов API, worker и контрольного подключения — 82 соединения при лимите PostgreSQL 96.

PostgreSQL 16.15 выделен в отдельный локальный экземпляр: порт 55433, `shared_buffers=64MB`, `fsync` и `synchronous_commit` включены. Основной и проверочный стенды используют другой экземпляр. Внешний Telegram выключен. Все адреса доступны только на этом компьютере; доступ через локальную сеть отменён.

В R44 свободно было около 17,5 ГБ физической памяти. Для того же кода и профиля кэш отдельного экземпляра увеличен до 512 МБ параметром запуска; файл конфигурации не редактировался. До прогона совпали количества ранее сохранённых строк в 11 таблицах, прошли 12 проверок клинических связей и сохранились 3000 результатов. Это изменение не решило ограничение максимума. После прогона нагрузочные API, proxy, worker и PostgreSQL штатно остановлены; файлы баз сохранены. Вариант с 12 API не запускался: пользователь запросил очистку ресурсов и публикацию результатов.

## Приёмка и обновление

Полный серверный набор: **286/286**, 184,76 секунды; профильные проверки — 33 и 29. Интерфейсные 125 проверок и сборка переиспользованы из предыдущего среза: совпали все 101 исходный файл интерфейса. После полного набора проверены 260 файлов без изменения исходников. В браузере проверены пациент, врач, администратор и координатор, включая ширину 375 px. Новых клинических решений или задач при показе не создавалось.

Перед миграцией проверены отдельные backup/restore для нагрузочной, основной и QA-баз. Создание и удаление индексов выполняются конкурентно; на восстановленных копиях проверен обратный переход. Контрольные суммы таблиц сохранены, последовательности проверены на отсутствие конфликтов будущих ID. При первом сравнении нагрузочной копии проверяющий скрипт использовал другой часовой пояс; исправление UTC/ISO подтвердило совпадение. Исходная база при этой ошибке не изменялась.

Индексы применены на всех трёх стендах. Основной API и QA перезапущены: health 200, по 12 проверок целостности без нарушений, 21/5 клинических результатов и прежние неизменяемые записи сохранены. Очередь после нагрузки обработана полностью; восемь проверок связности нагрузочных данных не выявили нарушений.

Для другого окружения: сделать резервную копию, выполнить обычный `alembic upgrade head`, затем запустить API. `READ_AUDIT_DB_POOL_SIZE` по умолчанию равен 1 и не допускает дополнительных соединений сверх этого числа. Учитывать резерв каждого API/worker в бюджете соответствующего экземпляра PostgreSQL. Если конкурентное создание индекса прервано, сначала проверить наличие и валидность индексов; повторный запуск не должен скрывать невалидный индекс. Обратный переход проверять на восстановленной копии, сохраняя рабочие данные.

Далее — локализация оставшегося длинного хвоста и повтор того же профиля после обоснованного изменения конфигурации. Частоту действий для окончательной приёмки нужно согласовать; текущий профиль и порог не ослабляются автоматически. Клинические случаи Авиандра и правовая готовность остаются отдельными открытыми требованиями.
