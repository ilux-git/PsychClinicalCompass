# Проверка восстановления и технические замеры

Инструменты предназначены для учебного стенда с синтетическими данными. Для Python нужны зависимости из `requirements-dev.txt`; для копирования — клиентские `pg_dump`/`pg_restore` версии сервера PostgreSQL. Приложение остаётся модульным монолитом с двумя БД; проверка ниже восстанавливает только Compass, без записи в МИС.

## Backup/restore

Скрипт `scripts/verify_backup_restore.py` читает URL из окружения. Секреты не передаются аргументами процесса и не выводятся. Архив содержит все данные выбранной Compass, включая хеши паролей: хранить его в локальном игнорируемом `outputs/` с доступом только команды. Архив/отчёт не коммитить.

Подготовить отдельную **новую пустую** БД на тестовом PostgreSQL, например `compass_restore_test` с владельцем `compass`. Создание БД выполняет администратор своего учебного сервера. Существующую БД для этого не очищать. Source/target должны иметь разные имена; target обязательно заканчивается на `_restore_test`.

В новом PowerShell-терминале с активированным Python-окружением, из корня проекта, для локального учебного PostgreSQL из README:

```powershell
$env:COMPASS_DATABASE_URL = 'postgresql+asyncpg://compass:compass@127.0.0.1:5432/compass'
$env:RESTORE_TEST_DATABASE_URL = 'postgresql+asyncpg://compass:compass@127.0.0.1:5432/compass_restore_test'
python scripts/verify_backup_restore.py --output outputs/restore-check-01
```

Это демонстрационные реквизиты README. Для другого стенда использовать его параметры через защищённое окружение. Скрипт не загружает `.env` автоматически. Если утилиты PostgreSQL не в PATH, добавить `--pg-bin 'C:/Program Files/PostgreSQL/16/bin'` или свой каталог. Повторная проверка требует новой пустой target-БД и нового пустого output-каталога; инструмент не удаляет данные и не использует `--clean`.

Порядок проверки:

1. До записи проверяет отличное имя target и отсутствие пользовательских отношений, функций и типов.
2. Открывает read-only repeatable-read транзакцию источника, экспортирует MVCC snapshot. В этой же версии данных получает таблицы, число строк и SHA-256 канонически упорядоченного DB JSON; `pg_dump` использует тот же snapshot.
3. Повторно проверяет пустоту target; `pg_restore` восстанавливает архив одной транзакцией с остановкой при ошибке, без переноса владельцев/ACL.
4. Сверяет набор таблиц, counts/checksums; проверяет, что следующее значение каждой возрастающей прикладной последовательности больше максимального ID. Последовательности не являются MVCC-данными, поэтому их точное совпадение с текущим source при конкурентных записях не утверждается.
5. Сохраняет `compass.dump` и `report.json`: время backup/restore, размер/хеш архива, показатели таблиц и проверки последовательностей; без строк пациентов/паролей.

При ошибке исходная БД не меняется. Ошибка утилиты выводится без её SQL/содержимого; не публиковать сырые PostgreSQL-логи. Если target успела успешно восстановиться, повтор уже будет отклонён как запись в непустую БД. Скрипт проверяет данные и пригодность ID, но не восстанавливает внешнюю МИС, роли/ACL, инфраструктуру, секреты или весь сервис.

## Контрольное время API

Работающее демо, учётная запись врача, новый PowerShell-терминал с `requirements-dev.txt`:

```powershell
$env:API_BENCHMARK_USERNAME = 'doctor'
$env:API_BENCHMARK_PASSWORD = 'doctor-pass-123'
python scripts/benchmark_api.py --base-url http://127.0.0.1:8000 --samples 30 --output outputs/api-baseline.json
```

Login нужен только для получения сессии; все измеряемые запросы — GET. По одному прогреву и 30 последовательных запросов для `/health`, `/auth/me`, `/patients`, `/alerts/inbox?limit=20`, `/analytics/engagement`. Отчёт содержит successes/errors, HTTP-коды, p50/p95 методом nearest-rank и максимум. Тела ответов, JWT, логины/пароли в отчёт не попадают. Код завершения ненулевой при ошибках. Это проверка малого синтетического набора с конкурентностью 1; целевая нагрузка и SLA не заданы.

## Внутренняя очередь врача

`GET /alerts/inbox?limit=20&before_id=...` доступен только врачу и только по текущим пациентам. Counts относятся ко всей открытой очереди; `before_id`/`next_before_id` ограничивают страницы. Закрытые события доступны в карточке, но не входят в очередь.

`POST /alerts/{id}/presented` фиксирует серверные время/автора и один аудит на пару событие–врач. UI вызывает его, когда минимум половина строки видна в активной вкладке. После передачи пациента другому врачу его показ учитывается отдельно. Этот факт не меняет status, decision, назначение в МИС и не подтверждает человеческое прочтение. Принятие в работу остаётся отдельной кнопкой и API.

Начало технического интервала — `outbox_events.created_at`, то есть поступление данных. Дата клинического измерения, особенно backdated seed, не служит началом. Поля `latency_seconds`: поступление → создание события / показ в очереди / принятие врачом. Отсутствующий или некорректный отрицательный интервал возвращается `null`. Целевое время реакции не выдумывается. Polling worker и UI по умолчанию 5 с; фонового внешнего оповещения нет.

## Проверенный результат 23.10.2026

- PostgreSQL 16.15, Windows, native API на 8780, 10 синтетических пациентов. Backup: **0,270 с**, restore: **0,427 с**, архив **73 376 байт**. Совпали **18 таблиц**, проверены **17 последовательностей**. Попытка использовать восстановленную непустую target отклоняется.
- На восстановленной БД отдельный процесс приложения: login, health, свои пациенты, история шкал и inbox — HTTP 200; admin inbox — 403. Рабочая Compass и МИС не изменялись процедурой восстановления.
- API: 150/150 успешных измеряемых GET, ошибок 0. p95: health **3,665 мс**, auth/me **4,728 мс**, patients **5,290 мс**, inbox **5,390 мс**, engagement **6,938 мс**. Это один локальный контрольный прогон.
- Новый синтетический PHQ-9 с отдельной версией `delivery_probe_v1`: событие создано через **1,759 с**, показано через **9,001 с**, вручную принято через **31,250 с**. Клиническое решение после принятия остаётся `pending_review`, MIS write false. Время ручного действия не является гарантией реакции врача. Проба добавляет одну отдельную числовую точку в сохранённый native demo и не смешивается с `demo_numeric_v1`.
- Полный backend-прогон **66 passed in 36.48s**; после добавления проверки отката presentation/audit и защит CLI — **10 passed in 3.34s** прицельно. В совокупности покрыт 71 уникальный тест; без skips. `alembic check`: расхождений нет; fresh/backfill/downgrade/upgrade входят в полный прогон. TypeScript/Vite build success.
- Браузер: сигнал доступен с обзора, сначала только видимая строка отмечена показанной, отдельное принятие, переход к своим исходным данным; мобильный 390×844, viewport восстановлен. Снимки и подробные JSON находятся локально в `outputs/`.

Это доказательства инженерной части C01/C03/C05/C11 и T01/T04/T06. Полный C05 требует согласованных критических правил, внешнего маршрута/дежурства и резервного действия. Промышленные RTO/RPO, нагрузочная ёмкость, клиническая эффективность и правовое соответствие этими замерами не устанавливаются.
