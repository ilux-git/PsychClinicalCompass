## Ближайшие решения для полезного MVP

### N01 / P0 — общая анкета сопровождения, уточнённый A02

**Принимаем ли предложенные C1–C7 из раздела 4 обзора как общее ядро для сопоставимой аналитики, сохраняя возможность врачу добавлять собственные формы? Какие пункты нужно исправить?**

Предложено спрашивать отдельно: готовность к конкретному шагу, понимание цели, доверие способу помощи, полезность приложения, барьеры, выполнение шага и необходимость помощи. Для ядра предлагаются словесные ответы, явные «не применимо/не могу оценить/не хочу отвечать», без итогового индекса личности. Период авторского ядра предлагаю явно указывать врачом; сравнивать только сопоставимые периоды/версии. Стандартные PHQ/GAD сохраняют своё утверждённое временное окно.

Смысл решения: нужен общий сопоставимый вопрос; сумма любых авторских вопросов разных врачей не даст сравнимую «лояльность». Не нужно заново сочинять всю анкету — можно ответить «ядро подходит» и перечислить правки. Ответственный за медицинские тексты — отдельный B02.

### N02 / P0 — что считать проблемным прекращением помощи, уточнённый A03

**Какие статусы эпизода клиника различает и когда «не вернулся в рекомендованное окно» становится поводом для контакта, а когда — подтверждённым прекращением помощи? Кто подтверждает этот исход?**

Предлагаемый словарь: активное сопровождение; согласованная пауза; плановое завершение; перевод к другому специалисту; прекращение раньше согласованного плана; исход неизвестен. Просроченный контакт предлагается отдельным сигналом, который сам по себе не равен потере клиента. Размер окна следует хранить в плане/профиле с автором, а не придумывать универсальные 30 дней.

Пример: после согласованного окончания курса нет нового визита — возможный успех, а не потеря. Перенос визита клиникой не равен неявке пациента. У вчера включённого пациента ещё не закончился месяц наблюдения. Нужны правила для этих ситуаций, а не одна общая дата последнего визита.

Можно ответить списком статусов, правилом окна и ролью подтверждающего. Если у клиники готового правила нет, это вопрос для брифинга; в демо неопределённые случаи остаются неизвестными.

### N03 / P0 — данные плана/визита и следующий шаг

**Какая МИС/система записи является источником и какие из полей реально есть: рекомендация следующего контакта/окно, запись на дату, состоявшийся визит, перенос/отмена с инициатором, причина и история изменения? Кто в клинике может подтвердить этот контракт?**

Для хакатона используем только синтетические данные; персональные выгрузки не нужны. При отсутствии готового подключения достаточно согласованного примера структуры. МИС остаётся read-only. Разделить назначения Compass и фактические визиты обязательно: без второго нельзя посчитать реальное удержание.

**Кто в MVP отвечает пациенту на заявленное затруднение и проверяет результат — лечащий врач или отдельный координатор?** Предложение первого прохода — врач. Если нужен координатор, надо определить отдельную ограниченную роль; администратор обезличенной сводки от этого не получает карточки/клиническую переписку.

## Следующие продуктовые решения

### N04 / P1 — лекарства: вопрос на брифинг по прямому поручению пользователя

**Из какой конкретно базы/МИС врач получает лекарственное назначение: есть ли ID препарата/формы, расписание, автор и версия; кто отвечает за этот справочник?** Если ввода врача достаточно для демо, это отдельный простой источник, а не имитация уже работающей интеграции.

Право пациента добавлять произвольные позиции/расписания уже принято. Предложение — отдельный личный список с сохранением любого описания, без молчаливого изменения врачебного назначения. Для автоматического напоминания остаётся определить: часовой пояс; изменение времени/курса; нерегулярные и «по потребности» режимы; канал при закрытом приложении и допустимость текста лекарства в уведомлении. Эти параметры не означают автоматическую рекомендацию дозировки/отмены. Неизвестный факт приёма остаётся неизвестным.

### N05 / P1 — баллы: не перечень действий, а правила начисления

**Баллы в первом MVP — только личный прогресс или их уже можно обменивать; какие веса, лимит и период начисления утвердить для трёх разрешённых действий?**

Предлагаю начать с нематериального прогресса и простой равной единицы за завершённую форму, за допустимое действие ведения расписания и за запись дневника; это гипотеза, не доказанный тариф. Чтобы не стимулировать формальные повторы, нужен отдельно согласованный лимит для начислений, без ограничения числа личных записей. Повтор запроса не начисляет второй раз; редактирование/импорт не должно позволять неограниченное повторное получение.

Предлагаемые условия: одинаковая награда при плохом самочувствии/сообщении о невыполнении; личный и общий дневник равноправны; число препаратов и доз не увеличивает баллы. Нужен ответ именно об экономике/периоде, а не повторное подтверждение уже выбранных трёх действий.

### N06 / P1 — структура дневника и жизнь записи

**Для первого структурированного дневника подходит ли предложенный минимум: время наблюдения, «сейчас/итог дня», необязательная словесная оценка самочувствия, влияние на выбранное повседневное действие, текст и отдельное sharing? Какие поля исключить/добавить?**

Это авторская запись, не диагностическая шкала. Дневник добровольный, приватный по умолчанию — текущая основа уже есть. Отдельный вопрос клиническому/правовому владельцу: как редактировать/удалять записи, сколько хранить их и что происходит с доступом при смене врача. Предлагаю не выдавать отзыв sharing за стирание уже прочитанного или медицинского документа. Политика не выбирается агентом из общего исследования.

### N07 / P1 — структура наблюдения врача: предложение вместо неопределённой «адекватности»

**Подходит ли шаблон «рекомендация/период → факт и источник → направление/затруднение → альтернативное объяснение → следующий шаг/ответственный/срок → повторный результат»? Какие дополнительные клинические поля обязательны?**

Предлагаю источник отмечать словами «со слов пациента / наблюдал врач / подтверждено событием / требуется уточнение». Числовая «достоверность» и автоматическое исправление ответа пациента не предлагаются: подтверждённого для этого универсального инструмента не найдено. Приватность повторно не согласуется — только врачу. Операционное подтверждение устранения барьера отличается от клинической оценки.

## Подключения и организационные границы

### N08 / P2 — фактические приложения и устройства после выполненного исследования

**Какие телефоны, часы и дневники уже используются командой/целевой клиникой? Достаточно названия приложения, Android/iPhone и модели устройства; кто может вести нативный компонент, если он нужен?**

Предложение: собственный дневник — основной; первый внешний перенос — один выбранный CSV/архив Daylio или eMoods либо уже используемого Day One/Bearable/Journal. Автоматическое здоровье — HealthKit/Health Connect или один актуальный vendor API по фактическому парку. В [исследовании](INTEGRATIONS_RESEARCH.md) описаны данные/ограничения, пользователю не требуется самому разбираться в API. Личные медицинские данные для выбора не нужны.

### N09 / брифинг перед реальным пилотом — политика организации

**Кто является владельцем политики доступа/агрегации, хранения/удаления и допустимого использования внешних сервисов? Какой контур допускается для пилота?**

Настраиваемость сводки уже принята. Научного универсального безопасного k нет; владелец политики задаёт допустимые значения/срезы и права изменения. Текущий режим скрывает числа до настройки, а не подтверждает юридическую анонимность. Облачные дневники и API могут добавлять внешних обработчиков — это нужно сопоставить с требованием ТЗ об ЭМК/контуре. Для синтетической демонстрации не требуется выдавать её за согласованный реальный пилот.
