# Демо-ЭМК: предпросмотр, одобрение и квитанция

Основание — [видение команды](TEAM_VISION_2026-10-25.md). Первый синтетический маршрут реализован26.10. **Это не запись во внешнюю ЭМК и не юридическая ЭЦП**. Приёмник сохраняет отдельную квитанцию в Compass; действующий коннектор МИС остаётся только для чтения.

## Как показать

Врач открывает «План работы» или «План и задачи» в карточке. У задачи, созданной из ответа на авторский опрос, раскрывает **«Передача в демо-ЭМК»**. Видны пациент/ID демо-МИС, точная версия/вопросы/ответ, сохранённое действие и отдельная проверка. После проверки содержимого врач ставит отметку и нажимает «Одобрить этот пакет». Затем отдельной кнопкой передаёт его симулятору. До второго действия квитанции нет. При отказе одобрение сохраняется; повтор не создаёт второй документ/квитанцию. Незавершённая задача не превращается в выполненную.

| Маршрут | Назначение |
| --- | --- |
| GET `/patients/{patient_id}/tasks/{task_id}/emr-preview` | Сохранённые сведения, SHA-256 канонического JSON и последнее одобрение/квитанция |
| POST `/patients/{patient_id}/emr-documents` | Одобрение точного hash/ревизии с явным boolean-подтверждением и ключом повтора |
| POST `/patients/{patient_id}/emr-documents/{document_id}/simulate-transfer` | Отдельное подтверждённое принятие локальным симулятором |

Текущая схема — `limbus-emr-demo/1`: ссылка на synthetic MIS ID; исходный ответ и версия опроса; задача/действие/проверка; явная симуляция подписи. Схема внешней МИС не утверждена. Первые источники ограничены ответом на авторский опрос через связанную задачу; частные заметки и дневник не экспортируются.

## Проверенный срез26.10

Первый проверяемый маршрут использует существующую задачу врача с исходным ответом на авторский опрос: точные вопросы/версия/ответ → описание действия и отдельный статус проверки → предпросмотр JSON → одобрение точного hash → отдельное принятие локальным синтетическим приёмником. Незавершённое действие и неизвестный результат сохраняют свой статус, без подмены завершением. У других типов источников в этом срезе нет экспорта; это ограничение первой реализации, не медицинское правило.

Три перехода: GET-предпросмотр без записи, явный POST-акт одобрения, отдельный POST-акт приёма симулятором. Автор и время сохраняются на сервере. Изменившаяся задача/привязка требуют нового предпросмотра; повтор того же одобрения или приёма возвращает прежний результат. Неверный ключ с другим содержимым отвергается. До отправки проверяются роль врача, конкретный пациент, источник и согласованная привязка к MIS ID. Приватные заметки/дневник, другие ответы и полная карточка не включаются.

Приёмник — отдельная логическая запись в Compass, с явным `synthetic=true`, `external_delivery=false`, `legally_valid=false`; HTTP-запроса во внешнюю МИС нет. Его запись и событие аудита атомарны в одной БД, внешнего outbox-действия в этом локальном переходе нет. Запись в существующую read-only MIS запрещена. Это позволит показать разрешённую эмуляцию, но не закроет буквальное требование о реальной прямой передаче без хранения у третьих лиц.

## Исторический образец25.10

Ниже сохранён первоначальный проект для истории обсуждения. Это не текущая API-схема; актуальная реализация и её версия описаны выше.

```json
{
  "schema_version": "compass-emr-demo/1-draft",
  "synthetic": true,
  "patient_reference": {"system": "synthetic-mis", "id": "EXAMPLE-PATIENT"},
  "revision": 1,
  "section": "follow_up_observation",
  "content": {
    "source": {"type": "survey_submission", "id": "EXAMPLE-SOURCE", "version": 1},
    "observation": "Синтетический пример: пациент сообщил, что ему не подходит расписание.",
    "physician_action": "Обсудить удобное время контакта.",
    "verification": {"status": "pending", "basis": null}
  },
  "review": {"status": "pending", "actor_id": null, "reviewed_at": null},
  "destination": {"system": "emr-simulator", "status": "not_transferred"},
  "signature": {"kind": "simulation", "legally_valid": false}
}
```

Этот формат не пытается угадать `Kev/Tiny Jev`. Названия полей/разделов — предложение нашей команды, подлежащее отображению на реальную схему после её получения. Врачебное наблюдение, действие и отдельная проверка остаются разными полями; исходный ответ не переписывается.

## Исходная последовательность проектирования

1. Лечащий врач выбирает разрешённый ему источник. Сервер проверяет роль **и связь с пациентом**; администратор/координатор не получают пакет.
2. Врач видит пациента, происхождение/версию, точный текст и раздел назначения. Личный дневник без разрешения не включается; не переносится вся карточка «на всякий случай».
3. Отдельное одобрение относится к точному неизменному содержимому/ревизии. Для него сохраняются автор, время и hash канонического содержимого. Изменение источника или текста требует нового предпросмотра/одобрения.
4. Только одобренный пакет может попасть в **синтетический приёмник**; повтор одного ключа не создаёт второй документ. Отклонённый/ожидающий пакет не передаётся. Одобрение и ответ приёмника — разные события.
5. В интерфейсе явно различаются «черновик», «одобрен врачом», «принят симулятором», «ошибка передачи». Последнее сохраняет одобренную ревизию для повтора. Подпись обозначена симуляцией, поле `legally_valid=false` сохраняется.

Эти проверки выполнены для описанного первого синтетического маршрута: чужая роль/пациент, hash/ревизия, конкурирующие повторы, отказ приёмника и атомарность с аудитом. Они не подтверждают совместимость с будущей внешней схемой или реальную доставку.
