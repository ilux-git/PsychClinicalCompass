> Уточнение от 22.10.2026: это исходный план. Пользователь разрешил реализацию и перенёс главный фокус на причины потери клиентов, выполнение рекомендаций, авторские опросы и мотивацию. Текущее исполнение — в .planning/STATE.md и ROADMAP.md; проверка — в docs/VERIFICATION.md. Неутверждённые бизнес-правила — в docs/QUESTION_QUEUE.md.

Подготовлено и проверено 21 октября 2026 года по коду, Excalidraw и 17-страничному PDF. Команда: два участника с ИИ-агентами.

**Рекомендация:** за первые два дня собрать один законченный маршрут наблюдения и обработки события. Дни 3-4 использовать на проверку, удобство и живой тестовый Telegram. Полный набор 12 модулей из PDF за этот срок не является базовой целью.

Подтверждено пользователем: симулятор Telegram достаточен, живой бот при наличии времени; работающая LLM не обязательна. Остальной состав ниже - предложенный план реализации, а не уже выполненные функции или утверждённые медицинские правила.

## 1. Что есть сейчас

Backend уже содержит FastAPI, две PostgreSQL-базы, async SQLAlchemy, три миграции, JWT/bcrypt, анкеты PHQ-9/GAD-7, сообщения, webhook и polling worker. Frontend, login, чтения карточек/истории анкет, алертов, заметок, доступности и клинического подтверждения пока нет.

Основные разрывы, которые нельзя прятать за интерфейсом:

- GET истории чата по коду доступен admin вопреки заявленным ограничениям.
- Worker помечает TG-сообщение sent без отправки в Telegram API.
- Риск анкеты создаёт outbox event, но worker не превращает его в рабочий Alert.
- Внешний chat_id ошибочно сопоставляется с mis_id; перед настоящим Telegram это нужно заменить.
- В двух базах расходятся имена двух пациентов, а PatientMapping не заполняется.
- История выбирает первые 100 сообщений, health всегда содержит status=ok, автоматические тесты не сохранены в репозитории.

Это выводы из исходников. Синтаксис 34 Python-файлов и конфигурация Compose проверены. Сборка, БД и API в текущей сессии не запускались: Docker установлен, но его Linux engine сейчас недоступен.

## 2. Результат двухдневного MVP

**Врач входит -> выбирает синтетического пациента -> видит данные MIS и историю -> пациент заполняет форму или пишет -> событие сохраняется -> врач видит объяснение и алерт -> подтверждает действие, создаёт заметку/задачу -> результат остаётся в истории.**

Дополнительно воспроизводится ветка недоступности врача и отдельный согласованный учебный кризисный случай с резервным маршрутом. Никакая внешняя служба не считается принявшей обращение по одному нажатию ссылки.

Минимальные интерфейсы:

| Интерфейс | Минимальная функция |
|---|---|
| Doctor Web | Список своих пациентов, карточка, две точки шкал/история, чат, очередь алертов, заметка/задача, подтверждение, ручная доступность |
| Patient Telegram / Mini App simulator | Мобильный экран: анкета, короткий самоотчёт, чат, статус врача и учебный резервный маршрут |
| Doctor Telegram simulator | Компактная панель уведомлений и ответа через ту же историю; явная маркировка симуляции |

Все три представления используют одни сущности и API. Симулятор работает от авторизованного пользователя; произвольный patient_id или выбор роли в браузере не предоставляют доступ к чужим данным.

## 3. Граница функций

| Область | База MVP | Упрощение |
|---|---|---|
| Доступ | Login, текущий пользователь, роль + связь с пациентом | Без управления организацией и устройствами |
| Две базы | 10 согласованных карточек, mapping, видимый источник данных | MIS только read-only; недоступность показывается явно |
| Опросы | Сохранение и история PHQ-9/GAD-7, детерминированный score | Тексты/источники согласовать; без конструктора шкал |
| Чат | Одна история, последние сообщения и курсор, ответ врача | Polling вместо WebSocket/SSE на первом проходе |
| События | Атомарный outbox, один worker, защита результата от дублей | Без нового брокера и многопроцессной оркестрации |
| Правила | Небольшой набор версионированных, объяснимых учебных правил | Без LLM, нового диагноза и подбора терапии |
| Алерты | Создание, принятие врачом, закрытие, причина и время | Без сложного SLA-движка и автоматического дежурства |
| Решение врача | Подтвердить/отклонить, причина, журнал в Compass | Не выдавать это за изменение назначения в MIS |
| Заметки/задачи | Приватная запись, связь с событием, простая задача со статусом | Без полноценного task manager |
| Приверженность | Короткий самоотчёт и unknown при отсутствии ответа | Без расчёта «эффективности лечения» по активности |
| Доступность | Ручной available/busy/offline/on_leave и понятное ожидание | Без календаря смен и реального внешнего crisis API |
| Аудит | Кто, когда, над каким объектом выполнил ключевое действие | Без промышленной подсистемы ИБ |

Новые источники/пороги/противопоказания не придумывать. Текущий код использует порог score >= 10 и отдельный flag PHQ-9 item 9; это существующая учебная реализация, не клиническая валидация. Положительный item 9 сам по себе не означает доказанную непосредственную угрозу жизни.

## 4. Архитектура и минимальный контракт

Сохранить текущий модульный монолит, FastAPI, async SQLAlchemy, Alembic, две PostgreSQL-базы и существующий outbox. Не заполнять все 12 каталогов пустыми заглушками. Redis/ARQ не требуют отдельного переустройства ради первой демонстрации.

Предложение для UI: один React + Vite + TypeScript frontend с врачебным и мобильными экранами. Зависимости пока не установлены. Базовые чтения/записи - REST, обновление - polling с курсором. Сначала общий контракт ответа, затем параллельная работа участников. Публичного дизайна или готового UI-макета материалы не содержат.

Ближайший контракт, который нужен frontend:

- `POST /auth/login`, `GET /auth/me`.
- `GET /patients`, `GET /patients/{id}`, `GET /patients/{id}/timeline`, `GET /patients/{id}/assessments`.
- Существующие `POST /assessments/responses`, GET/POST диалога; добавить idempotency key и догрузку истории.
- `GET /alerts`, `POST /alerts/{id}/acknowledge`; закрытие и отклонение - минимальные явные операции, контракт согласовать перед реализацией.
- `POST /clinical-decisions/{id}/confirm`, создание приватной заметки/задачи, `PATCH /doctors/me/availability`.
- Создание/чтение структурированного самоотчёта в adherence, без изменения назначений.

Не переносить существующие URL под новый префикс и не менять backend-стек ради единообразия.

Назначение владельцев ниже предлагается по зонам ответственности; имена и навыки участников не предполагаются.

| Этап | Участник A: backend и данные | Участник B: frontend и демонстрация | Готовность этапа |
|---|---|---|---|

| День 2, первая половина | Rule result -> один Alert -> подтверждение; минимальные notes/tasks, adherence, availability и аудит | Алерты/основания, подтверждение/отклонение, заметка, самоотчёт, offline/учебный резервный маршрут | Врач обрабатывает событие; unknown и ручное решение сохраняются корректно |

| День 4, если доступен | Backup/restore в отдельной БД, нагрузочные замеры, закрытый стенд | Финальный прогон, презентация, видео и резервный сценарий показа | Проверены повторяемость и восстановление демонстрации |

Ориентир для первых двух дней - около 14-18 активных часов каждого участника с агентами; это оценка, не утверждённый режим работы. Оставить примерно 20% времени на интеграцию и исправления. Если сквозной маршрут не работает к концу первого дня, дополнительные интеграции откладываются: оставшееся время идёт на завершение основы.

Один владелец всех Alembic migrations и общих схем API - участник A. Участник B владеет frontend и демо-сценариями. Не поручать двум агентам одновременно правку одних файлов. Интегрировать короткими PR после законченного поведения.

## 6. Три демонстрационных сценария

1. **Плановое наблюдение.** Врач открывает P001/P003, пациент отправляет анкету и сообщение, врач видит историю/динамику и отвечает, создаёт приватную заметку. Показать единое сообщение в Web и симуляторе.
2. **Повод для врачебной оценки.** Согласованные тестовые ответы/структурированная жалоба создают объяснимое событие и один алерт. Врач видит источник, версию правила и missing_data, подтверждает или отклоняет следующий шаг. Неответ в самоотчёте остаётся unknown.
3. **Врач недоступен.** Врач переводит статус в offline. Плановое сообщение сохраняется; ожидание объяснено. Отдельное заранее согласованное кризисное тестовое событие показывает резервный маршрут. Клик не запускает обращение и не меняет статус на «помощь оказана».

Десять карточек P001-P010 из PDF нужны как согласованный набор демонстрационных данных. Три перечисленных маршрута проверяются полностью. Остальные карточки должны явно показывать свой сценарий/недостающие данные; наличие карточки не выдаётся за полностью реализованную ветку всех медицинских правил.

Три специфических сценария Авиандра нельзя корректно вывести из названия препарата и общего описания. Нужны исходный конкурсный кейс и согласованные клинические правила; до этого допускается только честное состояние «требуется проверка / недостаточно данных», без выдуманного назначения.

## 7. Приёмка и тесты

Проверки, которые нельзя вырезать ради срока:

- Login: неверный пароль, истёкший/отсутствующий токен; разграничение двух врачей, двух пациентов и admin.
- Каждое чтение/изменение карточки, истории, заметки, сообщения, алерта и подтверждения проверяет принадлежность пациента.
- Шкалы: допустимые длины/значения, суммы и границы существующих флагов; raw answers и form_version сохраняются; PHQ-9 item 9 не превращается автоматически в критическое состояние.
- Дубли: повтор отправки формы/сообщения и повтор обработки outbox не создают новые бизнес-объекты.
- Данные: все 10 mappings согласованы, повтор seed не плодит записи, unknown не превращается в ноль или пропуск лекарства.
- Журнал: нельзя применить клинический шаг без врача; подтверждение и причина сохраняются; приватная заметка не открывается пациенту.
- Отказы: потеря сети, недоступность MIS и worker, перезапуск; UI не показывает ложную успешную доставку.
- Сквозная проверка трёх сценариев через интерфейс и повторный запуск с чистыми учебными данными.

Предлагаемые инструменты: pytest + HTTPX и PostgreSQL для API/транзакций, несколько unit-тестов чистого scoring, один короткий браузерный smoke по ролям. SQLite не подменяет проверку PostgreSQL JSONB/asyncpg. Не строить большой тестовый фреймворк заранее.

| AC-01 доступ, AC-02 две базы, AC-03 шкалы | Обязательно проверить |
| AC-04 TG/Web | Проверить на явно обозначенном симуляторе; live TG дополнительно |

| AC-10 ошибка MIS, AC-11 аудит | Обязательно для основного маршрута |

## 9. Первый шаг реализации

При поручении начать MVP выполнить подготовленный 01-01-PLAN: настоящий запуск -> исправление доступа -> login -> согласованные пациенты и минимальный API. Одновременно второй участник начинает UI по зафиксированному контракту. Новую архитектуру, живой Telegram и LLM в начало работ не ставить.

До внедрения новых клинических веток нужны конкретные учебные кейсы, согласованные источники/тексты шкал и резервный маршрут. Они не блокируют запуск, доступ, карточку и чат.
