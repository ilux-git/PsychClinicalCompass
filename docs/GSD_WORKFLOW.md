# GSD для хакатона

## Установка

Используется [GSD Core](https://github.com/open-gsd/gsd-core), пакет `@opengsd/gsd-core@1.18.0`, локальный профиль `core` для Codex. Нужен Node.js 24+.

В корне репозитория:

```powershell
npx.cmd --yes @opengsd/gsd-core@1.18.0 --codex --local --profile=core --no-legacy-cleanup
```

Установщик обязателен для адаптации под Codex; не копировать команды из исходников вручную. В этой рабочей папке установка выполнена из распакованного npm-пакета тем же официальным `bin/install.js`. Версия подтверждается файлом `.codex/gsd-core/VERSION`, профиль - `.codex/.gsd-profile`.

В профиль входят 8 навыков: `gsd-new-project`, `gsd-discuss-phase`, `gsd-plan-phase`, `gsd-execute-phase`, `gsd-phase`, `gsd-help`, `gsd-update`, `gsd-surface`. В текущем проекте новый проект повторно не инициализировать: `.planning/` уже подготовлен.

Локальные навыки будут доступны в следующем ходе при открытой папке проекта. При необходимости их инструкции можно прочитать непосредственно из `.codex/skills/`. Если интерфейс не обнаружил их после обновления, открыть эту папку как рабочую папку проекта; глобальная установка не требуется.

Установщик предупредил, что не смог записать глобальный `~/.gsd/defaults.json`. Для этой установки используются явные локальные настройки `.planning/config.json`; проверка локальной версии и профиля обязательна. Обход ограничений на глобальную запись не выполнялся.

## Режим работы

| Настройка | Значение и смысл |
|---|---|
| Профиль установки | `core`: 8 навыков, без отдельных конфигураций агентов |
| Модель | `inherit`: текущая выбранная модель без автоматического переключения |
| Объём плана | `coarse`, 1-3 задачи на рабочую итерацию |
| Отдельные исследователь и проверяющий план | Выключены; исследование по конкретной необходимости |
| Отдельные UI-, AI- и Nyquist-процессы | Выключены |
| Проверка результата | Включена; предметные тесты выполняются в текущем агенте |
| Автозапуск дополнительных агентов / worktree | Выключен |
| Переходы | Продолжать в уже разрешённом объёме без повторного «продолжать?» |
| Новые бизнес-правила / новый объём | Уточнить у пользователя |
| Git | Работа в существующей ветке; перед началом реализации создать `agent/<task-name>` |

`workflow.code_review=false` отключает отдельный процесс ревью; проверка доступа, миграций, клинических ограничений и результата задачи остаётся обязательной по AGENTS.md. Политика разрешений и sandbox не ослабляются.

## Одна итерация

1. Прочитать STATE.md, цель фазы и требования. Выбрать одну проверяемую задачу.
2. Зафиксировать файлы, результат и способ приёмки; обычно 5-15 строк достаточно.
3. Выполнить минимальное изменение в рамках поручения.
4. Проверить нужный API/сценарий/права. Шкалы, доступ, события и подтверждение врача требуют содержательных тестов.
5. Записать результат, ограничения проверки и следующий шаг. Если поручение продолжается - сразу выполнять следующий разрешённый шаг.

Для формального запуска фазы можно использовать `$gsd-plan-phase 1` и `$gsd-execute-phase 1` после поручения начать реализацию. Установленный адаптер допускает inline-выполнение, когда отдельные агенты не запрошены. Не подменять им полный многопроцессный GSD-проход в отчёте.

Для мелких исправлений отдельная фаза не нужна: короткая задача, проверка и запись в состоянии. Профиль `full`, дополнительные плагины, отдельная «фаза ИИ» и глобальная конфигурация для текущего MVP не требуются.

Диагностика GSD выводит W010 об отсутствии глобальных GSD agents. Для выбранного core/inline режима отдельные агенты намеренно не установлены; не исправлять это предупреждение установкой полного профиля. GSD CLI и локальные конфигурационные значения проверяются отдельно.

Проверка структуры первого плана прошла: три задачи, ошибок/предупреждений нет. Проверка согласованности ROADMAP/STATE/планов прошла без замечаний. Активные ссылки локальных навыков и hook проверены после размещения репозитория в корне рабочей папки.

## Артефакты проекта

- PROJECT.md: цель, подтверждённые ограничения и предложенные решения.
- REQUIREMENTS.md: короткая проверяемая граница MVP.
- ROADMAP.md: четыре фазы и условия готовности.
- STATE.md: где остановились и что делать дальше.
- docs/CODEBASE.md: текущий код, разрывы и границы проверки.
- docs/MVP_PLAN.md: общий план для команды, сроки и демонстрация.
- phases/: подробный план только ближайшей фазы; последующие уточняются по факту.
