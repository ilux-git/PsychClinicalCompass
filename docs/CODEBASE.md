## Разрывы, влияющие на план

1. **Admin читает историю диалога по коду.** `app/modules/messaging/service.py:72` проверяет ограничения только для patient и doctor; `router.py` для GET не исключает admin. Это противоречит README и PDF. Нужен явный запрет и отрицательный API-тест.
2. **Telegram send является симуляцией.** `app/workers/outbox_worker.py:15` только меняет статус сообщения на sent. Внешнего вызова Telegram API нет. Интерфейс должен честно показывать симуляцию.
3. **Risk event теряет полезную обработку.** В том же worker после обработчика каждое событие получает processed, но для `assessment.risk_detected` нет создания Alert. Риск-флаг пока не даёт врачу рабочей очереди событий.
4. **Привязка канала некорректна для реального TG.** `app/modules/messaging/service.py:103` сопоставляет `Patient.mis_id == chat_id`. Перед живой интеграцией нужна отдельная привязка канала к пользователю/пациенту.
5. **Данные MIS и Compass расходятся.** Seed: Nikolai Fedorov и Sergei Morozov; MIS SQL: Nikolai Petrov и Sergei Ivanov для соответствующих ID. PatientMapping не заполняется seed. Нужен один источник демо-фикстур.
6. **История возвращает первые 100 сообщений.** `get_history` сортирует по возрастанию и применяет limit. После длинного диалога новые сообщения могут перестать попадать в выдачу. Нужны последние сообщения и курсор догрузки.
7. **Health постоянно возвращает status=ok.** `app/main.py:26` делает это даже при false у проверок БД. Состояние доступности для UI/развёртывания нужно явно определить и проверить.
8. **Нет нормального входа и интерфейса.** README предлагает копировать JWT из seed. Это непригодно как основной пользовательский маршрут демонстрации.
9. **Outbox ещё не является гарантией exactly-once.** Нет блокировки выбранных событий для нескольких workers, ключа материализованного результата и счётчика попыток. В первом MVP использовать один worker, а результат обработки защищать уникальным event key; для реальной доставки отдельно решить повторы.
10. **Сборка требует проверки layout.** `Dockerfile` копирует несколько каталогов в один destination; app дополнительно монтирует Alembic из checkout. При первом настоящем запуске проверить наличие `alembic/env.py` и цепочку миграций внутри образа, а не полагаться на bind mount.

Это выводы из чтения исходников; сетевой запрос, демонстрирующий обход доступа на запущенном стенде, не выполнялся.

## Границы проверки

- Синтаксис всех 34 Python-файлов app/ и alembic/ проверен через compile без выполнения импортов.
- `docker compose config --quiet` прошёл после создания локального .env; новый JWT-секрет сгенерирован и не выводился.
- Docker CLI есть, но Docker Desktop Linux engine не доступен. Сборка, миграции, seed и API-тесты с БД в этой сессии не запускались.
- Зависимости Python приложения и frontend не устанавливались; встроенный Python использован только для чтения/проверки.
- Ссылка на прежний архив и исходный конкурсный кейс в PDF не означает, что эти материалы были доступны или обработаны.
