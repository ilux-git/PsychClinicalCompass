# Усиление доступа: план и границы

Состояние26.10: оба нижеописанных технических среза реализованы, o33/p34 применены после backup/restore-проверок. Backend177/177, frontend88/88; [отчёт и нативный выход](evidence/access-2026-10-26/report.json). Следующие разделы сохраняют исходный план, границы и порядок проверки. Это не общая правовая/клиническая приёмка.

Основание — обязательные пункты1/10/11 и разрешение25.10 срочно закрывать пробелы. Первый срез: защита входа и отзыв текущего токена. Следующий отдельный срез: журнал чтений. Реальные данные, новые полномочия администратора и отключение чужих учётных записей не включаются.

## Первый срез

- У каждого нового JWT собственный случайный `jti`. Сохраняются60-минутный срок из текущей настройки и загрузка настоящей роли из БД. Прежние выпущенные приложением токены с `sub/iat/exp`, но без `jti`, остаются совместимыми до выхода/истечения.
- `POST /auth/logout` отзывает только credential из заголовка запроса; не принимает токен другого человека из тела. Хранится SHA-256 токена и срок, без самого JWT. Повторный выход идемпотентен. Все защищённые маршруты проверяют отзыв вместе с пользователем в БД. Другие сессии того же пользователя сохраняются.
- Счётчик входа — атомарное резервирование попытки по нормализованному логину и адресу прямого клиента. Заголовку `X-Forwarded-For` по умолчанию не доверяем. Инженерные настройки:10 попыток/300 секунд; успешный вход сбрасывает свой счётчик. Настройки ограничены валидируемыми значениями, сохранены между процессами через PostgreSQL. Ошибка возвращает429 и `Retry-After`, без раскрытия наличия пользователя.
- Проверка bcrypt выполняется вне основного event loop; для неизвестного пользователя также проверяется фиктивный hash. Пароли/токены не попадают в аудит и ошибки.

## Изменяемые области и проверки

`access/models.py`, `access/router.py`, `core/security.py`, `core/config.py`, `api/deps.py`, регистрация моделей и новая миграция `o33_access_safeguards`. Потребители: все API с `CurrentUser`, seed/tests, Telegram-связь и кнопка выхода клиента. Отрицательные ролевые/пациентские проверки обязательны; МИС остаётся только для чтения.

Проверки: независимость двух сессий, повторный выход, прежний формат токена, неверный/истёкший токен, атомарный предел конкурирующих входов, окно/сброс и отсутствие обхода заголовком. Затем полный backend и клиентские сценарии выхода/позднего ответа.

## Выпуск и восстановление

1. До изменения сохранённых стендов — custom-format резервные копии основной и QA Compass, проверка читаемости оглавления; без reset/seed и без изменений MIS.
2. Проверить upgrade и охрану downgrade на отдельных пустых/тестовых БД. Существующие таблицы/строки не переписываются: добавляются только таблицы безопасности.
3. Применить расширяющую миграцию, затем перезапустить API. Старые токены сохраняют доступ, если не отозваны. Подключить явный выход клиента к серверному endpoint; автоматическое истечение не вызывает цикл logout-запросов.
4. Откат приложения к версии, не проверяющей отзыв, может снова разрешить отозванные credentials: такой откат нельзя выполнять как обычное восстановление. Безопасный путь — исправление вперёд с сохранением таблицы отзыва. Для аварийного возврата оператор сначала закрывает внешний доступ и отдельно управляет секретом/повторным входом; автоматически это не выполняется.
5. Downgrade откажется удалять таблицу с ещё действующими отзывами. Резервная копия сохраняется; восстановление поверх работающих данных без отдельного поручения не запускается.

Журнал чтения проектируется отдельным проверяемым срезом: актор, шаблон ресурса/идентификаторы и исход запроса без содержимого ответов и произвольных query-строк. Его внедрение должно сохранять чтение, права и транзакции предметных функций; результаты текущих83/156 тестов не выдаются за проверку ещё не реализованного аудита.

## Второй срез: журнал чтения · 26.10.2026

Новая отдельная таблица `read_access_events`: проверенные в БД идентификатор/роль актора, шаблон серверного маршрута, числовые идентификаторы запрошенных объектов, HTTP-исход, внутренний UUID и время. Журнал содержит и разрешённые чтения, и отказы403/404/422 уже аутентифицированному человеку. Неверный/отозванный credential не получает чужое авторство. Запросы без идентифицированного актора, static/health и записи POST/PATCH в этот журнал не входят; предметный аудит записей сохраняется.

Содержимое ответов, ФИО, сообщения, диагнозы, токены, IP и произвольные query-параметры не сохраняются. Из query допустим только числовой `patient_id`, если он действительно объявлен параметром маршрута. Идентификатор запрошенного пациента не означает разрешённый доступ. Публичного API журнала нет; клинические права администратора не расширяются.

Запись аудита должна завершиться **до отправки начала ответа**. Если она не удалась, клиническое тело не отправляется, возвращается503. Сессия предметного запроса закрывается после сериализации, до отдельной транзакции аудита (`Depends(..., scope="function")`): чтение не коммитит случайные предметные изменения и не удерживает одно соединение в ожидании второго. Проверить это запросами с пулом из одного соединения. Защищённые GET получают `Cache-Control: no-store`.

Изменяемые области: модель audit, зависимость CompassSession/CurrentUser, отдельный ASGI middleware, регистрация в main и миграция `p34_read_access_audit`. Потребители — все аутентифицированные GET, в том числе списки/агрегаты; потоковых ответов с БД сейчас нет. Проверки: точный актор/HTTP-исход/шаблон, своя/чужая карточка, запрет роли, ошибка валидации, отсутствие текста/credentials в записи, отказ хранилища до отправки данных, один connection и параллельные чтения. Затем полный backend. Новая миграция добавляет только таблицу/индексы; downgrade при непустом журнале запрещён. Сохранённые стенды менять только после новой резервной копии и восстановления в отдельную БД.

Это технический журнал MVP, без утверждения о сертифицированной неизменяемости, согласованном сроке хранения или общей правовой приёмке. Эти решения остаются у оператора будущего пилота.
