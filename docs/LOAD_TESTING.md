## Что выполняется

Базовый профиль: назначения, баллы, PHQ/GAD-история, лекарства, карточка, запись дневника с начислением, сообщение в симулятор с outbox; врачи — каталог пациентов, доска, аналитика; аналитик — защищённая сводка.

Расширенный `LOAD_EXTENDED_WORKFLOWS=1` дополнительно отправляет одинаковые повторяемые ответы на реальные синтетические назначения, читает состояние запросов поддержки, явно помечает часть сообщений как запросы поддержки; врач читает события, берёт задачи в работу с revision и создаёт связанное действие с ответом. Примерно каждое 11-е подходящее сообщение создаёт запрос поддержки. Ключевые слова не участвуют. Нет подмены медицинских данных случайными диагнозами или реальных внешних сообщений.

После расширенного прогона:

- 1000 сохранённых ответов на опросы; 64 821 записей дневника и 65 821 записей журнала начислений, включая эти 1000 опросов.
- 64 954 сообщения, 659 обращений, 154 связанные команды врача, всего 1154 задачи.

Времена worker — сохранённые timestamps до окончательного commit пакета. Они не являются подтверждением провайдера или показом в браузере. UI очереди/переписки пока обновляется polling с интервалом 5 с; 500 мс не объявляются временем появления сообщения у другого пользователя.

## Настройка API

Для исторического успешного профиля использовались **8 API-процессов**, Compass pool 8 + overflow 0 на процесс, MIS pool 2 + overflow 0, отдельный worker. `.env.example` содержит эти параметры; Docker Compose берёт `API_WORKERS`. Существующий `.env` не меняется при обновлении автоматически — новые параметры надо перенести. Параметры кластера PostgreSQL и реальные ресурсы проверяются отдельно.

Worker при наличии работы продолжает разгружать пакеты; после пустой выборки ждёт `OUTBOX_POLL_INTERVAL_SECONDS` (для профиля 0.1). Retry/backoff, лимит попыток, savepoint и идемпотентность сохранены. Подробные успешные события переведены в DEBUG, ошибки логируются без клинического текста. Брокер или микросервисы не добавлены.

Обычный одиночный процесс подходит для разработки малого демо; проверку 1000 пользователей он не прошёл. Не переносите результат восьми процессов на запуск с одним.

Сохраните настройки в игнорируемом `work/load.env`: все обязательные параметры `.env.example`, URL новых БД, `LOAD_MIS_ADMIN_DATABASE_URL` той же МИС с owner-доступом, `LOAD_TEST_MODE=true`, `TELEGRAM_ENABLED=false`, `ALLOW_LOAD_TEST_SEED=1`, уникальный `LOAD_TEST_RUN_ID` длиной от 16 символов, новый путь `SYNTHETIC_MIS_FIXTURE_PATH` внутри `work/`. Сохраните один run ID для всей этой когорты; новый ID не сбрасывает базу.
4. Из активированного Python-окружения выполните:

```powershell
python -m dotenv -f work/load.env run -- python scripts/load_scenario.py seed --manifest outputs/load-test/scenario.json
python -m dotenv -f work/load.env run -- python scripts/load_scenario.py export-k6-users --manifest outputs/load-test/scenario.json --output work/load-users.json
```

Seed сам применяет миграции и отказывается перезаписывать непустую схему или существующий JSON. Экспорт JWT отказывается работать на обычной базе и писать вне игнорируемых `work/`/`outputs/`; файл должен быть новым. Не публикуйте эти файлы. Истёкшие JWT экспортируйте в новое имя.

5. В двух терминалах с тем же виртуальным окружением:

```powershell
python -m dotenv -f work/load.env run -- python -m uvicorn app.main:app --host 127.0.0.1 --port 8791 --workers 8 --no-access-log
```

```powershell
python -m dotenv -f work/load.env run -- python -m app.workers.outbox_worker
```

6. В третьем терминале задайте пути и запустите генератор:

```powershell
$env:K6_NO_USAGE_REPORT = 'true'
$env:LOAD_USER_FILE = (Resolve-Path work/load-users.json).Path
$env:LOAD_MANIFEST = (Resolve-Path outputs/load-test/scenario.json).Path
$env:LOAD_BASE_URL = 'http://127.0.0.1:8791'
$env:LOAD_PATIENT_VUS = '1000'
$env:LOAD_RAMP = '10s'
$env:LOAD_DURATION = '60s'
$env:LOAD_THINK = '1'
$env:LOAD_EXTENDED_WORKFLOWS = '1'
$env:LOAD_SERVER_WORKERS = '8'
$env:LOAD_RUN_STARTED_AT = (Get-Date).ToUniversalTime().ToString('o')
$env:LOAD_DRIVER_CONTEXT = 'native local execution'
$env:LOAD_REPORT_FILE = Join-Path (Get-Location) 'outputs/load-test/k6-current.json'
python -m dotenv -f work/load.env run -- k6 run scripts/roles_load.k6.js
```

Перед записью k6 проверяет `/_load-test/context`: matching run ID, synthetic=true и external_delivery=false. На обычном приложении этот endpoint возвращает 404. Ненулевой код завершения k6 означает провал хотя бы одного порога; пустое поле или отсутствие отчёта не являются успешным тестом. Отдельный Python HTTPx-драйвер `load_scenario.py run` оставлен для диагностики; его слабая масштабируемость не выдаётся за независимое подтверждение ёмкости API.

После прогона проверьте события/аудит/начисления и отсутствие backlog, затем сохраняйте точные параметры стенда, код/commit, отчёт и его hash. Синтетическая нагрузочная БД не входит в малый демонстрационный seed и не подключается вместо dev.
