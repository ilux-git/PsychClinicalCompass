# Clinical Compass: роли, рабочий процесс и показатели

Дата: 22.10.2026. Этот документ задаёт продуктовый план после первого технического MVP. Статусы «предложено» не означают реализованную функцию или согласованное правило.

Дополнение 23.10.2026: получено ТЗ «Задача.txt», подготовлена [полная сверка](TZ_GAP_ANALYSIS.md). Для соответствия ТЗ дополнительно обязательны клинические сценарии с Авиандром, терапия/маршрутизация, источники, экстренное оповещение и решение по ЭМК. План организационной сводки ниже не заменяет эти требования; предлагаемый порядок их закрытия указан в сверке.

## 1. Цель и основной цикл

Клиника должна видеть, где прерывается сопровождение, какие препятствия называет пациент и что происходит после реакции врача. Для этого нужны три связанных контура:

1. **Пациент:** получил понятное назначение → сообщил состояние и барьеры → увидел, что ответ сохранён → получил следующий шаг.
2. **Врач:** заметил изменение/пробел → проверил первичный ответ → связался или создал задачу → зафиксировал действие → проверил повторное наблюдение.
3. **Администратор:** увидел агрегированную проблему → выбрал организационное действие → сравнил следующий период и полноту наблюдений. Карточки и клинические решения остаются у врача.

Сейчас надёжно реализован сбор ответов и техническая запись действий. Полного контура «действие → повторное наблюдение → исход визита» пока нет. Наличие модулей и успешные технические тесты не означают завершённый продуктовый workflow.

## 2. Что подтвердил аудит до исправления видимости

- В работающем стенде найдено 16 числовых PHQ-9 у 8 из 10 пациентов. В seed отсутствует GAD-7. Два пациента без истории — допустимый пример отсутствия наблюдений.
- API истории возвращает дату, сумму, версию и флаги, но не отдельные ответы. История спрятана во вкладке «Клинические данные» у врача; у пациента отдельного экрана нет.
- Аналитика врача показывает назначения и ответы; время до ответа, сопоставимая динамика шкал и связь с дальнейшим действием ещё не собраны в общий маршрут.
- В текущей МИС нет визитов, отмен, планового возврата и причин отказа. Фактическое удержание и изменение возвратов после вмешательства пока не вычислить.
- Пользователь разрешил администратору общие обезличенные показатели. Сначала требуется выбрать содержимое сводки, затем способ ограничения малых групп. Q03 больше не означает «роль неизвестна».

## 3. Workflow по ролям

| Роль / шаг | Что видит и делает человек | Сохранённый результат | Состояние |
|---|---|---|---|
| Пациент: старт | Видит, какие опросы назначены, срок и кому будут доступны ответы | Конкретное назначение и его версия | Есть для авторских опросов |
| Пациент: состояние | Заполняет согласованные PHQ-9/GAD-7; видит свою историю и предыдущие ответы | Отдельные ответы, сумма, версия, время | Числовой API и история с ответами реализованы; тексты, назначение и прохождение клинических форм в UI — Q05 |
| Пациент: барьер | Отмечает препятствие, намерение продолжать и выполнение рекомендации | Исходный ответ без автоматического вывода об уходе | Есть |
| Пациент: участие | Видит факт отправки, прогресс и историю; может написать врачу | Один факт завершения на назначение | Есть; экономика наград — Q04 |
| Пациент: следующий шаг | Получает согласованный ответ/план повторного контакта | Сообщение врача; в будущем связанное повторное назначение | Чат есть; единый план сопровождения и контрольный срок ещё нужны |
| Врач: начало дня | Видит очередь событий, неотвеченных назначений и открытых задач; выбирает пациента | Объяснимый повод для проверки, без автоматической срочности | Данные есть в разных местах; единая очередь нужна |
| Врач: разбор | Сверяет динамику одной шкалы/версии, ответы по пунктам, барьер и историю | Ручная оценка на основе исходных данных | Частично есть; видимость шкал исправляется отдельно |
| Врач: действие | Ответ, заметка с источником, задача, при необходимости новое назначение | Автор, время, источник заметки и статус задачи | Есть по отдельности; у задачи сейчас только связь с пациентом, нужна связь с первичным ответом |
| Врач: контроль | Сравнивает повторное измерение и исход после действия | Отмеченный последующий результат; неизвестность при отсутствии данных | Нужны связь действия с наблюдением и согласованный контрольный срок |
| Администратор: обзор | Смотрит охват, ответы, заявленные барьеры и организационную обработку | Общая картина с формулой, периодом и знаменателем | Предлагаемый состав ниже; endpoint/UI ещё нет |
| Администратор: решение | Выбирает организационную гипотезу: расписание, понятность сопровождения, способ связи | Действие клиники и период проверки | После согласования состава; автоматические причины не придумывать |
| Администратор: проверка | Сравнивает периоды с учётом состава пациентов и полноты данных | Наблюдаемое изменение; причинность отдельно не доказана | Требует сопоставимых периодов и данных о визитах для удержания |

## 4. Предлагаемый состав сводки администратора

Первый экран должен отвечать на организационные вопросы. Предлагаются четыре основных блока и один отдельный блок качества наблюдения; медицинские разрезы согласуются отдельно.

### A. Охват сопровождения — «Кого мы вообще слышим?»

- Число зарегистрированных пациентов; число получивших хотя бы одно назначение.
- Охват назначениями и доля назначений с ответом.
- Пациенты без назначений и назначенные пациенты без обратной связи — отдельные группы.

Это позволяет отличить отсутствие интереса от ситуации, когда человеку ещё не предложили ответить. Термин «активные пациенты клиники» пока не использовать: для него нет определения/источника.

### B. Барьеры и намерения — «Что люди называют причиной сложности?»

- Частоты **согласованных структурированных** вариантов барьеров: расписание, стоимость, непонятные шаги и т. п.
- Намерение продолжать / сомнение / отказ отвечать, с числом ответивших и пропусков.
- Дословные тексты, названия/варианты произвольных авторских вопросов и цитаты в админку не переносить: они могут содержать персональные сведения. Разные версии вопросов не смешивать.

Нужен согласованный общий шаблон или явное сопоставление вопросов. Нельзя объединять все вопросы с `purpose=barriers` только по названию назначения: содержимое и смысл могут различаться.

### C. Выполнение рекомендаций — «Получается ли согласованный план?»

- Доли самоотчётов «получилось» и «не получилось» среди оценимых ответов.
- Отдельно: «не могу оценить», «не применимо», пациенты вообще без самоотчёта.
- Результат подписан как самоотчёт, а не фактический приём препарата или медицинская приверженность.

Свободный текст рекомендации пока не даёт стабильного идентификатора. На первом проходе считать показатели на уровне записей; для динамики конкретного плана нужен структурированный объект рекомендации.

### D. Обработка обратной связи — «Превращаются ли ответы в действия?»

- Медианное время от назначения до ответа.
- Медианное время принятия события врачом; число событий, ещё ожидающих разбора.
- Доля задач, завершённых за выбранный период, с явно указанной когортой.
- Связь «ответ → действие → повторное наблюдение» — следующий шаг, когда будет определено, что считается действием и когда ожидается контроль.

Скорость обработки не равна качеству лечения. SLA и сроки допустимого ожидания не задавать самостоятельно.

### E. Качество наблюдений / возможное дополнение: динамика состояния

- Базовая часть: сколько пациентов имеют хотя бы одно и повторное измерение PHQ-9/GAD-7.
- Возможное дополнение после выбора состава: среднее парное изменение балла, отдельно по шкале и версии; размер парной группы и число исключённых непарных наблюдений.
- Не показывать диагнозы, индивидуальные суммы/ответы, флаги пункта 9, редкие сочетания и списки пациентов. Не называть снижение балла доказанной эффективностью клиники.

Нужно решить, нужны ли администратору сами агрегированные клинические баллы или достаточно охвата/повторных измерений. Этот выбор должен предшествовать правилу скрытия малых групп.

## 5. Контракты вычисляемых показателей

Общие правила: период `[since, until)`, время с часовым поясом; нулевой знаменатель → «нет данных», не 0%; разные шкалы/версии и разные когорты не складывать. Каждая карточка содержит числитель, знаменатель, период, источник и ограничение интерпретации. Расчёты ниже — спецификация, а не заявление, что все они уже реализованы.

| ID / показатель | Формула и единица наблюдения | Источник / период | Зачем нужен / готовность |
|---|---|---|---|
| M01 Охват назначениями | Уникальные пациенты с назначением / все зарегистрированные в Compass на момент расчёта | Patient; назначения созданы в периоде, общая популяция на момент отчёта | Видно, где отсутствует предложение участвовать; это не историческая активная база клиники; расчёт предложен |
| M02 Завершение назначений | Назначения с submission / все назначения выбранной когорты | SurveyAssignment.created_at в периоде; текущий статус на момент расчёта | Уже есть у врача; не считать процентом удержания |
| M03 Охват обратной связью | Пациенты с ответом по когорте / пациенты с назначением в этой когорте | Уникальные patient_id по назначениям/ответам | Один активный человек не увеличивает охват несколькими ответами; предложен |
| M04 Просроченные назначения | Без ответа и due_at < момент расчёта / назначения с наступившим сроком | Та же когорта; назначения без due_at исключены | Для очереди контакта; имеющийся абсолютный счётчик дополнить знаменателем |
| M05 Время ответа | Медиана submission.created_at − assignment.created_at, часы; только завершённые | Назначения выбранной когорты; рядом число незавершённых | Не скрывать неответивших за быстрой медианой; данные есть |
| M06 Доля барьера | Пациенты, выбравшие вариант / пациенты с ответом на этот вопрос; брать последний ответ каждого пациента по этой версии в когорте | Общий согласованный шаблон + версия + question_id; несколько вариантов допустимы | Один частый респондент не получает больший вес; у врача пока количества ответов, общая нормализация нужна |
| M07 Намерение продолжать | Пациенты каждой категории / пациенты с ответом; последний ответ по вопросу/версии в когорте, пропуск отдельно | Тот же согласованный шаблон/версия | Ранний сигнал для разговора; не churn |
| M08 Самоотчёт о выполнении | followed / (followed + not_followed), единица — отчёт | AdherenceReport.created_at в периоде | Unknown/not_applicable и отсутствие отчёта отдельно; данные есть |
| M09 Повторные измерения | Пациенты с ≥2 сопоставимыми ответами / пациенты с ≥1 | QuestionnaireResponse.created_at в периоде, отдельно form_type + form_version | Показатель полноты наблюдения; данных PHQ недостаточно для GAD, расширить фикстуры |
| M10 Парное изменение балла | Среднее (последний − первый) по каждому пациенту с ≥2 точками; один пациент — одна пара | Только одна шкала/версия, обе точки внутри периода; одинаковые времена не образуют продольную пару | Описательная динамика, не причинный эффект лечения; личная история требует вывода |
| M11 Время принятия события | Медиана acknowledged_at − created_at, часы | Alert.created_at в периоде; ещё не принятые считаются отдельно | Видна организационная задержка; timestamps есть, SLA не задан |
| M12 Завершение задач | Задачи со статусом done / задачи, созданные в периоде; открытые/просроченные отдельно | DoctorTask.created_at; состояние на момент расчёта | Не выдавать за факт контакта/изменения лечения; данные есть |
| M13 Ответ → действие | Ответы с согласованным связанным действием / ответы, по которым действие ожидается | Submission + source links; ожидание и допустимые действия надо определить | Сейчас корректно не считается: связь частичная, бизнес-правило отсутствует |
| M14 Фактический возврат | Вернувшиеся в согласованный срок / пациенты с ожидаемым возвратом и завершённым окном наблюдения | Визиты/отмены/плановый срок из МИС | Блокируется Q02/Q07; ещё не наступивший срок не считать уходом |

Для администратора эти расчёты требуют отдельного агрегирующего API с разрешённой схемой ответа. Нельзя просто скрыть имена на клиенте и использовать врачебный endpoint, возвращающий индивидуальные данные.

### Контрольный пример из текущего синтетического стенда

После добавления GAD-7 и сохранения прежних пользовательских демо-действий, на момент проверки:

- 10 пациентов; назначения есть у 9; хотя бы один ответ дали 6. Охват обратной связью среди назначенных — `6 / 9 = 66,7%`.
- 19 назначений, 10 завершены: `10 / 19 = 52,6%`. Это другая единица измерения; показатели не взаимозаменяемы.
- PHQ-9: 16 ответов у 8 пациентов, 8 сопоставимых пар. GAD-7: 13 ответов у 7 пациентов, 6 пар; один человек пока имеет только одну точку.
- Двое без истории шкал остаются без данных. Их нельзя включать в средний балл как нули.

Это проверка доступности числителей/знаменателей на синтетических данных, а не опубликованная админская сводка. Данные будут меняться при прохождении опросов; до согласования состава и защиты групп административного API нет.

## 6. Что не попадёт в сводку автоматически

- ФИО, ID пациента/МИС/аккаунта, контакты, чаты, диагнозы, назначения и заметки.
- Дословные ответы, произвольные тексты авторских опросов и ссылки на персональные карточки.
- Рейтинг врачей или вывод о качестве лечения по скорости ответа/среднему баллу.
- «Вероятность ухода», «эффективность терапии» и процент фактической приверженности без подтверждённых источников и определения.

После согласования блоков определить разрешённые периоды/разрезы, пороги малых групп, скрытие связанных ячеек и защиту от восстановления значения через вычитание. Просто удалить ФИО недостаточно, чтобы гарантировать обезличивание.

## 7. Порядок реализации

| Итерация | Результат для пользователя | Проверка готовности |
|---|---|---|
| 1. Видимые данные состояния | PHQ-9 и GAD-7 в синтетических данных; отдельные ответы, история и сравнение сопоставимых точек доступны своему врачу и пациенту | Проверены отсутствие/одна/две точки, версии, суммы, повтор seed и запрет чужого/admin-доступа |
| 2. Согласование сводки | Выбраны блоки A–E, формулы, источник и допустимый уровень детализации | Для каждой карточки понятны управленческий вопрос, знаменатель и ограничения; после этого согласована защита малых групп |
| 3. Администратор | Отдельный экран и агрегирующий endpoint только с выбранными показателями | В JSON/ошибках нет персональных данных и произвольного текста; проверены малые группы, вычитание, пустые периоды и роли |
| 4. Ежедневный маршрут врача | Общая очередь → первичный ответ/история → связанное действие → контрольный шаг | Один сценарий проходится целиком; задача и контакт различаются; неподтверждённые клинические правила не добавлены |
| 5. Удержание и проверка гипотез | Данные МИС о визитах, согласованный возврат/уход, связь с барьером и действием | Завершённые окна наблюдения отделены от ещё ожидаемых; наблюдаемая связь не выдаётся за причинность |

Один владелец миграций и контрактов; второй участник может вести UI после согласования схемы. Реальный Telegram и LLM не вытесняют эти итерации.

## 8. Решения, которые ещё нужны

1. Какие блоки A–E входят в первый экран администратора; нужны ли ему агрегированные суммы/динамика шкал или только полнота наблюдений.
2. После выбора состава: периоды, разрезы и правила скрытия малых/связанных групп.
3. Что считается потерянным клиентом и какой источник визитов доступен — Q02/Q07.
4. Утверждённые тексты/источники клинических форм и резервный маршрут — Q05/Q06.
5. Правила коммерческой мотивации — Q04. Согласование сводки не утверждает их автоматически.
