### Запуск новой локальной копии

Нужны Git и Docker с Compose. Из каталога репозитория:

```powershell
Copy-Item .env.example .env
```

В `.env` задайте собственный `JWT_SECRET`. Для новой локальной копии параметры двух БД и Redis уже соответствуют стандартному Compose. Затем:

```sh
docker compose up --build -d
docker compose ps
```

Откройте **[http://127.0.0.1:8000/](http://127.0.0.1:8000/)**. Единственный сервис `init` применяет миграции и создаёт исходные профили; API и worker запускаются после его успешного завершения.

Проверка состояния и журналы:

```sh
curl http://127.0.0.1:8000/health
docker compose logs --tail 100 app worker init
```

Остановка и повторный запуск сохраняют базы:

```sh
docker compose stop
docker compose up -d
```

### Обновление и обслуживание сервера

На VPS код расположен в `/opt/limbus/releases/`, активный выпуск — `/opt/limbus/current`. Настройки и резервные копии находятся в закрытом каталоге `/opt/limbus/shared/`. Файл `.env` содержит параметры развёртывания, `.env.runtime` — только настройки работающего приложения. Пароли SSH, владельца МИС и токен бота не включаются в репозиторий.

```sh
ssh root@104.238.29.90
cd /opt/limbus/current
docker compose -p limbus -f docker-compose.yml -f docker-compose.public.yml -f docker-compose.vps.yml ps
docker compose -p limbus -f docker-compose.yml -f docker-compose.public.yml -f docker-compose.vps.yml logs --tail 100 app worker gateway
```

Обновление выпуска: резервная копия обеих БД → сборка нового образа → проверка миграций и API → запуск новой версии с существующими томами → проверка HTTPS и кабинетов. В VPS-конфигурации `init` выполняет только миграции; повторного заполнения рабочего стенда нет.

После обновления существующего стенда до схемы v41 три клинических профиля добавляются отдельно, без замены прежних пациентов. Предпросмотр и применение:

```sh
docker compose -p limbus -f docker-compose.yml -f docker-compose.public.yml -f docker-compose.vps.yml exec -T app python -m app.db.seed_aviandr
docker compose -p limbus -f docker-compose.yml -f docker-compose.public.yml -f docker-compose.vps.yml exec -T app python -m app.db.seed_aviandr --apply
```

Повторный запуск сохраняет существующие профили, эпизоды и решения. На новой локальной копии эти профили создаёт `init`. Интеграционные сведения кейсов читаются из JSON; доступ МИС остаётся только на чтение.

### Данные для показа аналитики

На стенде 213 пациентов: исходные 13 профилей и 200 дополнительных. Вход: `cohort_patient001` … `cohort_patient200`, пароль `patient-pass-123`. Половина новых профилей закреплена за каждым врачом; исходные клинические кейсы сохранены. Общая воронка на момент проверки: 529 назначений → 413 открытий → 374 завершения. Есть разные барьеры, состояния лечения, задачи и результаты проверки. Время искусственно созданных ответов не смешивается с измеренным временем прохождения.

Добавление этой группы в новую копию (предпросмотр, затем применение):

```sh
docker compose exec -T app python -m app.db.seed_cohort
docker compose exec -T app python -m app.db.seed_cohort --apply
```

Повторный запуск не заменяет существующие записи. Для VPS используйте те же три Compose-файла и `-p limbus`, что в командах обслуживания выше.

Последние исходники дополнительно сокращают число запросов для карточки, историй, лекарств и прогресса. Они прошли **365 серверных тестов**, но эта последняя серия ещё **не опубликована на VPS и не прошла нагрузочное сравнение**: работа остановлена по просьбе пользователя. Опубликованные ранее оптимизации ускорили проверенный профиль примерно на 23%; строгий максимум 500 мс пока не достигнут. [Фактические результаты](docs/LOAD_TESTING.md).

Caddy обслуживает доверенный HTTPS на IP без отдельного домена и автоматически обновляет сертификат. PostgreSQL и Redis доступны внутри сети контейнеров, API — через HTTPS-шлюз. Docker и основные сервисы настроены на автоматический запуск.

Для повторного запуска текущего выпуска:

```sh
docker compose -p limbus -f docker-compose.yml -f docker-compose.public.yml -f docker-compose.vps.yml up -d --wait
```

Тома `compass_pgdata`, `mis_pgdata` и данные Caddy сохраняются при обновлениях. Команда `docker compose down -v` удаляет данные и для обслуживания стенда не используется.

## Технологии приложения

| Часть | Технологии и назначение |
|---|---|
| Сервер | Python 3.12, FastAPI, Pydantic: API, проверка входных данных и прав доступа |
| Работа с данными | SQLAlchemy Async, asyncpg, PostgreSQL 16, Alembic |
| Базы | Compass — данные приложения; отдельная МИС — чтение через роль `mis_reader` |
| Фоновые задачи | Транзакционный outbox и отдельный worker; Redis для вспомогательной инфраструктуры |
| Интерфейс | React 19, TypeScript, Vite, CSS-токены, Lucide, Motion |
| Telegram | Mini App на общих компонентах кабинетов, SDK, темы и безопасные отступы; парольный вход без постоянной привязки |
| Развёртывание | Docker Compose, Caddy, HTTPS, постоянные тома и резервные копии PostgreSQL |
| Проверки | pytest, React Testing Library, Node test runner, браузерные сценарии, axe-core и k6 |

Архитектура — модульный монолит. Опросы, история состояния, задачи, сообщения, мотивация, клинические события, источники и аналитика разделены на модули и используют общие механизмы авторизации и аудита. Клинические сведения не кешируются в браузере; Mini App хранит токен в памяти открытого приложения.

## Реализация требований ТЗ

| Требование и задача | Реализация в приложении |
|---|---|
| Раздельные роли и доступ | Кабинеты врача, пациента, администратора и координатора. Сервер проверяет роль и связь с конкретным пациентом при чтении и изменении данных |
| Связь врача с пациентом | Общая история переписки, явные запросы поддержки, исходный ответ пациента и переход из события в его карточку |
| Сопоставление с ЭМК | Связь по patient/MIS ID. Формирование JSON-документа из сохранённых сведений, точный предпросмотр, одобрение врачом и отдельная квитанция приёма |
| Подтверждение клинических действий | Врач фиксирует решение, действие и отдельный результат проверки. Клинические назначения и изменения терапии подтверждает врач; организационная передача уведомлений следует настроенному маршруту |
| Оценка и мониторинг состояния | PHQ-9 Золотарёвой 2023 года, GAD-7 и панический модуль PHQ. Ответы, даты, редакции, источники, исходное измерение и динамика доступны в карточке |
| Клинические сигналы | Согласованные границы PHQ-9/GAD-7, приоритеты HIGH/CRITICAL, источник сообщения и отдельное принятие уведомления. Для CRITICAL — немедленная оценка и контроль принятия через 5 минут; врач фиксирует вывод, действие и проверку результата |
| Экстренная помощь пациенту | В чате доступны ручные кнопки 112/103 и короткая инструкция; при критическом сообщении блок раскрывается сразу. Звонок подтверждает пациент на своём телефоне |
| Клинические кейсы Авиандра | Три подписанных профиля, временные срезы записей врача, переданная динамика EPDS, проверка сочетаний и недостающих данных. Система формирует гипотезу; врач исправляет или одобряет её, фиксирует действие и проверяет результат |
| Резервная маршрутизация | Выбранный врачом координатор получает организационное уведомление по ID пациента при недоступности врача или истечении срока принятия |
| Самоотчёты и приверженность | Расписание лекарств, исправляемые отметки, добровольный дневник, наблюдения о самочувствии и выбор доступа врача к записи |
| Персональные опросы | Врач создаёт, публикует и назначает собственные версии опросов. Пациент сохраняет черновик и отправляет ответы; врач видит конкретную версию и исходные сведения |
| Работа с причинами затруднений | Четыре направления обратной связи, барьеры со слов пациента, задача врачу или координатору, выполненное действие, повторная проверка и результат |
| Аналитика клиники | Обезличенные сводки охвата, прохождения опросов, причин, действий, сроков и проверенных исходов; минимальную группу задаёт администратор |
| Мотивация пациента | Опросы — по объёму заполнения; лекарственный отчёт и дневник — по 10 баллов, максимум по 10 в сутки на каждое направление. Создание/редактирование расписания — без баллов. Карта участия, недельный ритм, спокойный режим и обмен на купон; прежние начисления сохраняются |
| Клинические источники | У опросников сохранены версия, источник, условия применения и лицензия. Разные редакции и прежняя числовая история отображаются отдельно |
| Поддержка врачебного решения | Показаны исходные факты, основания и следующий шаг; приложение не устанавливает диагноз и не подменяет решение врача |
| Конфиденциальность | Разграничение по пациенту и роли, приватные заметки, управляемый доступ к дневнику, защищённые агрегаты, ограничение входа, отзыв сессии и журнал чтений до отправки ответа |
| Надёжность | Защита повторных команд, контроль версии при изменениях, атомарная запись действия и outbox, резервное копирование и проверка восстановления |
| Кроссплатформенность и нагрузка | Адаптивные кабинеты и Telegram Mini App; проверен профиль 1000 пациентов, 20 врачей и аналитика с интервалом действий 2 с на отдельном экземпляре VPS. [Условия и измерения](docs/LOAD_TESTING.md); максимум 500 мс требует дальнейшей оптимизации |

Даты, время и дневные пределы участия рассчитываются по Москве. Повторная отправка записи не увеличивает баланс; полученные ранее квитанции сохраняют исходную сумму.

Основной сценарий показа: **ответ пациента → выявленное затруднение → действие врача или координатора → отдельная проверка результата → сводка клиники**. У пациента этот цикл связан с опросами, дневником, расписанием и разделом «Мой прогресс».
